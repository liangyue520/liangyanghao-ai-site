# 拿到一个新项目，我为什么不再急着铺页面

接手项目时，我曾经很容易被界面吸引：拿到技术要求或原型图，就想尽快看到一个完整的页面。AI 可以很快生成菜单、列表和表单，看起来项目已经有了模样。但做过几次之后，我发现，如果没有先弄清楚数据和业务流程，后面很可能要反复返工。

在一个信息管理项目中，我拿到过已有代码、数据表和原型。最初，我把注意力放在页面与功能点上，后来才意识到：系统里原有的数据表是什么结构，新的数据从哪里来，导入以后由谁审核，审核后又在哪些界面使用，这些问题都需要先弄清楚。

如果只盯着某个页面，可能很快做出“导入”按钮，却不知道数据应该进哪张表；也可能先把展示页面做好，后来才发现要展示的数据还没有经过审核。每一步单独看都有内容，连起来却未必能支撑用户的完整操作。

后来遇到类似任务，我会先把技术要求整理出来，结合已有原型和代码，弄清几个问题：用户要完成什么操作？数据从哪里进入？哪些数据是正式的，哪些还在等待处理？每个模块接收什么、输出什么？有哪些已有能力可以直接复用？

原型图仍然很有价值。它帮助我理解界面的布局、入口和交互。但原型毕竟需要结合具体业务检查：有的图展示的是完整操作，有的只是功能示意。遇到入口缺失或流程不明确的地方，就要对照需求和现有实现补充，而不是只凭画面推测。

在三维客户端项目里，我把技术要求整理成 Markdown，再让 Codex 协助拆分成较小的开发单元，同时提供已有 B 端界面作为参考。这样做的好处是，一方面可以逐项推进，另一方面也能回头检查每项功能在整体流程中处于什么位置。

这不是说每个小改动都要先写一套完整设计。修一个明确的按钮问题，可以直接定位和验证；接手一个需求和数据关系都不清楚的系统，就值得先花时间梳理。对我而言，开发前多问一句“数据最终要去哪里”，常常比多生成一个页面更有用。
